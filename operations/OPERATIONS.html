운영 데이터 백업·복구

준비 완료: 암호화 도구와 모의 저장소 복구 테스트. 미실행: 실제 Netlify 백업 및 실제 복구 훈련. 이 문서와 operations 폴더는 public 밖에 보관합니다.

백업 범위

auth/users(암호 해시·salt 포함), players, names, scores, badges를 보관합니다. 로그인 세션·진행 중 플레이·중복 제출 claim·요청 제한 데이터는 제외합니다. deleted/ 삭제 이력도 보관합니다. 복구 후 재로그인해야 하며 진행 중 플레이는 복구되지 않습니다. 브라우저별 설정·로컬 최고점·게스트 기록은 포함되지 않습니다.

AES-256-GCM 인증 암호화와 scrypt 키 파생을 사용합니다. 복호화 검증과 레코드 해시 검사, 복원 후 전체 재읽기를 수행합니다. 암호를 분실하면 복구할 수 없습니다.

1. 운영 쓰기 중지

Netlify에서 PULSE_MAINTENANCE=1을 설정하고 적용된 배포를 확인합니다. 같은 저장소를 사용하는 모든 배포 컨텍스트와 예전 배포 주소, 별도 도구의 쓰기도 차단해야 합니다. 이 패치가 없는 예전 배포에는 유지보수 설정이 적용되지 않습니다. 실제 로그인·점수 API가 503을 반환하는지 확인하고 진행 중 요청이 종료될 때까지 기다립니다.

백업은 DB 트랜잭션 스냅샷이 아닙니다. 두 번 읽어서 변경 여부를 검사하지만 동시 쓰기를 완벽히 배제하지 못하므로 쓰기 중지가 필수입니다.

2. 로컬 환경 준비

프로젝트 루트에서 npm ci를 실행합니다. 아래 값은 본인 컴퓨터의 환경변수로만 설정합니다. 채팅·소스·공개 저장소에 넣지 마세요.

  • NETLIFY_SITE_ID: 운영 사이트 ID
  • NETLIFY_AUTH_TOKEN: 해당 사이트 접근 권한이 있는 개인 토큰
  • PULSE_BACKUP_PASSPHRASE: 백업 전용 긴 무작위 암호(20자 이상), 암호 관리자에 별도 보관
  • PULSE_DATA_STORE: 기본 pulse-five-ranking-v1, 변경했다면 실제 저장소 이름
  • PULSE_WRITES_PAUSED=yes: 쓰기 중지를 직접 확인한 후 설정하는 확인값

폴더 backups를 먼저 생성합니다. Windows는 폴더 ACL과 디스크 암호화도 확인하세요. 파일 모드 0600만으로 모든 OS의 접근 통제가 보장되지는 않습니다.

node operations/data-tool.mjs backup backups/2026-10-30.pulsebackup
node operations/data-tool.mjs inspect backups/2026-10-30.pulsebackup

기존 파일은 덮어쓰지 않습니다. 암호화 파일도 개인정보 백업으로 취급하고 public·Git·일반 공유 드라이브에 올리지 않습니다.

3. 새 저장소로 복구 훈련

원본 저장소와 다른 이름을 지정합니다. pulse-restore-로 시작하고 비어 있어야 합니다. PULSE_RESTORE_CONFIRM을 새 이름과 정확히 같게 설정합니다. 운영 저장소에는 직접 덮어쓸 수 없습니다.

node operations/data-tool.mjs restore backups/2026-10-30.pulsebackup pulse-restore-drill-20261030
node operations/data-tool.mjs verify backups/2026-10-30.pulsebackup pulse-restore-drill-20261030

중간 실패 시 부분 복구 저장소를 활성화하지 마세요. 원본은 그대로 유지됩니다. 새로운 빈 복구 저장소 이름으로 재시도하고 실패한 저장소는 Netlify에서 별도 정리합니다.

4. 복구본 활성화

운영 유지보수를 유지한 상태에서 복구본을 별도 비공개 사이트/컨텍스트에 연결해 계정 로그인·닉네임·개인 기록·랭킹을 검증합니다. PULSE_DATA_STORE 값을 새 저장소 이름으로 설정하면 연결됩니다. 라이브 사이트는 기본 이름을 유지합니다.

복구 도구는 원본 저장소의 최신 deleted/ 이력을 읽어 삭제된 회원을 복원 대상에서 자동 제외합니다. 이 이력에 접근할 수 없으면 복구를 중단합니다. 3년이 지난 백업도 복구를 거부합니다. 별도 수동 처리한 삭제 요청이 있다면 추가로 대조해야 합니다. 이를 확인하기 전 복구본을 공개하지 않습니다. 과거 개인정보가 다시 살아날 수 있기 때문입니다.

검증 후 운영 사이트의 PULSE_DATA_STORE를 복구본으로 변경·배포하고 마지막으로 PULSE_MAINTENANCE를 해제합니다. 현재 도구는 이 전환이나 원본 삭제를 자동 실행하지 않습니다.

보유·삭제와 주기

제안 운영 정책: 큰 변경 전 추가 백업, 운영 시 매일 암호화 백업, 월 1회 복구 연습. 실제 주기·보유기간은 운영자가 확정해야 하며 자동 스케줄은 아직 등록되지 않았습니다. 운영자 지정 보유기간은 최대 3년입니다. 그보다 짧게 보관할 수 있으며, 만료 백업과 별도 복제본까지 삭제하는 절차를 함께 운영해야 합니다. 백업 파일의 자동 삭제 스케줄은 등록하지 않았습니다. 다음 명령은 만료 파일을 먼저 목록으로 보여주며, --apply를 붙일 때만 복호화 검증을 마친 3년 이상 백업을 삭제합니다. 다른 암호를 사용하는 파일이 섞였거나 검증 실패가 있으면 삭제 전에 중단합니다.

node operations/prune-backups.mjs backups
node operations/prune-backups.mjs backups --apply

토큰 최소 권한·관리자 2단계 인증·암호화 보관·접근자 제한·삭제 요청 처리 이력·정기 복구 점검을 운영 기준에 포함하세요. 이 문서 작성만으로 운영 백업이 완료된 것은 아닙니다.
